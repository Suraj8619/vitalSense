# Decision log

Fifty-one decisions, each with the alternative that was rejected and the reason. This started
as §10 of [PLAN.md](../PLAN.md) and outgrew it.

The format is deliberate. *"Why did you choose X over Y"* is the question a project like
this exists to answer, and a decision recorded without its rejected alternative is not a
decision — it is a description. Several rows below record choices that turned out to be
wrong and were reversed; those are kept, because a log that only contains decisions that
survived is a log that has been edited to look good.

Grouped by theme rather than by number, since that is how they get asked about. The
numbering is chronological, so the gaps within a section are the project working on
something else.

**Where they came from:** every row was written the moment the decision was made, in the
same commit as the work. [BUILD_LOG.md](../BUILD_LOG.md) has the session that produced it.

### Architecture and build order

Why the system is shaped the way it is, and why it was built in this order.

| ID | Decision | Alternative rejected | Why |
|---|---|---|---|
| D-01 | Sim-first, hardware-second build order | Hardware first | Algorithm needs annotated ground truth to validate (a live sensor can't say if a beat was missed); hardware availability is the schedule risk, so it goes on the critical path last |
| D-02 | 360 Hz ECG sampling | 250/500 Hz | Matches MIT-BIH rate → identical filter coefficients and directly comparable validation between sim and device |
| D-03 | Thin edge / smart server split | Full DSP on ESP32 | Server-side DSP is testable against dataset, hot-swappable, and mirrors real monitor architecture (bedside unit + central station); ESP32 keeps only deterministic sampling + light notch |
| D-04 | Pan-Tompkins for QRS | ML classifier | Interpretable, defensible stage-by-stage in an interview, no training data pipeline needed, still the industry baseline; ML can be layered on later |
| D-05 | Plain WebSocket streaming | MQTT | One less broker to run; MQTT's QoS matters for fleets of devices, not one — and we handle outages with device-side buffering (SR-05). Know this trade-off cold for interviews |
| D-06 | Postgres, single docker-compose | K8s/RabbitMQ like AsyncForge | Right-sizing infra is the "mindset to simplify" line in the JD; AsyncForge already demonstrates the heavy stack |

### Signal processing

Choices inside the DSP: what to filter, what to detect, and when to refuse to answer.

| ID | Decision | Alternative rejected | Why |
|---|---|---|---|
| D-07 | Detection path filtered 5-15 Hz, separate from the 0.5-40 Hz display path | One filter chain for both | QRS energy peaks at 5-15 Hz; that band maximises detection but distorts the waveform a clinician reads. Real monitors keep the two paths separate for the same reason |
| D-08 | Absolute flat-line amplitude gate before the adaptive threshold | Adaptive threshold alone | An adaptive threshold rescales to whatever it is given, so on a detached electrode it locks onto microvolt numerical residue and reports a heart rate. Found by a self-test on constant-DC input |
| D-09 | Report heart rate as the median of instantaneous rates | 60 / mean(RR) | One spurious or missed beat shifts a mean far enough to trip an alarm; the median absorbs it. Combined with a physiological RR plausibility filter (0.25-3 s) |
| D-10 | Publish honest per-record results, including the bad ones | Tune thresholds per record, report the best | Per-record tuning inflates these numbers and degrades unseen signals. The useful fix is a signal-quality flag (SR-07), not a better-looking table |
| D-11 | Verification report generated by script, never hand-edited | Hand-written results table | A hand-maintained table drifts from the code silently; `dsp/validate.py` regenerates it and exits non-zero on requirement failure, so it can gate CI |
| D-14 | Detector refuses a sampling rate its coefficients were not designed for | Accept any fs and filter anyway | Silently applying 360 Hz coefficients to a 250 Hz stream would corrupt real patient data with no error; failing loudly is the safe behaviour |
| D-25 | Firmware is written to build for the host as well as the ESP32 | Build only for the target | A target-only build can only be verified on a board. A host build lets the firmware's own fixed-point filter be scored against the Python design on MIT-BIH, so the C implementation joins the same equivalence check as the JS port (D-13) instead of being taken on trust |
| D-33 | The PPG refractory period is derived per-recording by autocorrelation | A fixed minimum spacing between pulses | A PPG carries a dicrotic wave about a third of a cycle after the systolic peak. A spacing wide enough to reject it at 48 bpm rejects real beats at 180 bpm; one narrow enough for 180 bpm counts every dicrotic wave and doubles the rate — measured, exactly 2× at 48 and 72 bpm. This is the same failure Pan-Tompkins solves with T-wave discrimination, in a different signal |
| D-35 | The signal-quality metric withholds a number only on QRS energy concentration measured after the Pan-Tompkins integration, with its threshold derived from SR-01 | Withhold when the standard spectral SQIs (QRS-band share, baseline power, kurtosis) all fail | Kurtosis and the QRS-band share both fall for a *wide* QRS, so they cannot tell a noisy signal from a ventricular one. Built that way, record 119 — ventricular bigeminy on a clean trace — was 59.9 % unusable against 10.2 % for record 108 with severe baseline artefact: the monitor would fall silent exactly when the patient started throwing ventricular beats. It also inflated the published numbers by excluding the hardest beats, which is D-10's mistake in a new disguise. Integration normalises QRS width away, so the concentration measure cannot be triggered by an abnormal beat shape, and deriving its threshold from the ±5 bpm of SR-01 ties "too poor to report" to "cannot meet the requirement" rather than to a percentile of one database |
| D-36 | Pulse rate is the autocorrelation period, not a count of detected peaks | Count peaks, or take the median RR interval | On real ICU recordings both peak-based estimators ran 15–23 bpm *low*: beat amplitude varies with respiration in ventilated patients, so a prominence threshold silently drops the small beats and every dropped beat biases a count downwards. Autocorrelation is a whole-window measure and does not care how tall any individual beat is — mean error fell to 1.04 bpm on the same recordings. Peak detection is still used for the per-beat AC/DC windows, where individual beats are genuinely needed |

### Cross-implementation consistency

Three languages filter the same ECG. These are the rules that keep them the same filter.

| ID | Decision | Alternative rejected | Why |
|---|---|---|---|
| D-12 | One filter design in Python, generating C and JS coefficient files | Hand-transcribe coefficients into each language | Three implementations filter the same ECG (validation, firmware, server). Transcribing by hand means the validated pipeline and the deployed pipeline eventually differ, and nothing catches it |
| D-13 | Streaming detector scored against MIT-BIH like the offline one | Trust that the port is equivalent | "The causal port matches" is a measurable claim; `server/tools/validateStreaming.js` measures it on the same records, annotations and +/-150 ms window |
| D-38 | Peak picking is written out in both languages instead of calling a library | Use `scipy.signal.find_peaks` in Python and approximate it in JavaScript | A cross-language comparison only means something if both sides run the same algorithm. Depending on scipy's prominence semantics would have left the port approximating something it could not reproduce, and any disagreement afterwards would have been unattributable — is the port wrong, or merely different? Writing ~15 lines twice buys the ability to say the answer is neither |

### Wire protocol

The device-to-server contract, and what its shape encodes.

| ID | Decision | Alternative rejected | Why |
|---|---|---|---|
| D-15 | Frames are blocks of samples with a sequence number, not single samples | One WebSocket message per sample | At 360 Hz per-sample framing costs more in overhead than payload; `seq` gaps are what makes lost data detectable rather than invisible |
| D-16 | Absent sensor readings are sent as `null` | Repeat the last good value | Holding a stale reading makes a disconnected sensor look healthy - the most dangerous failure mode a monitor has |
| D-17 | Beats are reported as absolute sample indices with a frame anchor | Offsets into the current frame | Detection lags the R peak by more than one frame, so most offsets were negative and were being dropped - only ~8% of beats reached the dashboard |
| D-39 | The server speaks protocol v1 **and** v2 | Bump to v2 and reject v1 | D-14 refuses to *guess* at an unknown version, which is not the same as refusing a known one. A fleet does not reflash atomically, so rejecting v1 would black out every deployed device the moment the server is updated — a monitor going dark during an upgrade is a worse failure than one running an older frame format. Both versions are enumerated, tested, and their difference is visible downstream in `spo2Source` |

### Alarms

Designing against alarm fatigue, and what acknowledging an alarm may and may not mean.

| ID | Decision | Alternative rejected | Why |
|---|---|---|---|
| D-18 | Alarm debounce sits inside the requirement budget, not on top of it | 2000 ms debounce for a 2 s requirement | A debounce equal to the budget makes the requirement unmeetable by construction; measured 2.1 s, now 1.5 s debounce leaves 500 ms margin |
| D-19 | Asystole and signal-poor suppressed when a more specific alarm explains the fault | Fire every alarm whose condition holds | A detached lead is not a cardiac arrest, and a silent device has no signal to judge. Redundant alarms are the mechanism of alarm fatigue |
| D-20 | Sessions survive a disconnect for 30 s, then are reaped | Delete on disconnect / keep forever | Deleting immediately loses filter state across a WiFi blip (SR-05); keeping forever leaves finished sessions alarming DEVICE_SILENT indefinitely |
| D-44 | Acknowledging an alarm silences it for a bounded time that depends on severity, and the silence belongs to one episode | Acknowledge dismisses the alarm until the condition clears | An alarm that can be switched off while its condition still holds is an alarm that gets switched off. Acknowledging changes the clinician's awareness, not the patient — so the silence expires (60 s high, 120 s medium, 300 s low) and the alarm returns with its original onset time. Conversely a condition that clears and recurs is a *new* episode arriving unsilenced: the clinician silenced that event, not this one. Acknowledging an alarm that is not currently sounding is refused outright, since pre-silencing is the shortcut that makes the whole mechanism dangerous |

### Knowing when not to measure

The project's recurring theme: a monitor that says "I don't know" is safe; one that guesses is not.

| ID | Decision | Alternative rejected | Why |
|---|---|---|---|
| D-22 | Acquisition restarts and the rate is withheld for 3 s after electrodes reconnect | Keep filtering and detecting straight through | The reconnection step drives a transient through the IIR filters while the adaptive thresholds are still tuned to the flat line; the detection burst was displayed as 190 bpm tachycardia with signal quality "good". Bedside monitors blank the rate across this settling period for the same reason |
| D-23 | Stale values are withdrawn from the display, not left on screen | Keep showing the last received number | A number on a monitor is a claim about *now*. After 3 s without a frame the dashboard shows "--" and flags NO DATA rather than letting a clinician read a number that is no longer true |
| D-32 | SpO₂ is refused when the red and infrared pulsatile waveforms disagree in shape | Trust the ratio and flag only on beat-to-beat spread | Both wavelengths traverse the same arterial bed, so their AC waveforms must be near-identical in shape — anything that is not arterial pulsation perturbs them differently. Beat-to-beat spread cannot catch motion because a periodic artefact is *self-consistent*, the same trap as D-22: with the spread check alone a 95 % patient was reported at 86.9 % marked "good". Swept over 432 recordings, a 0.97 floor rejected every reading more than 2 % wrong while refusing 7.7 % of accurate ones |
| D-34 | The ratio-of-ratios → saturation curve is documented as an assumption, and R is reported alongside SpO₂ | Present the percentage as a validated result | The curve is fitted per sensor design against arterial blood-gas measurements from human desaturation studies. It cannot be derived and it cannot be validated in simulation. What simulation *can* verify is that R is recovered correctly from a waveform whose true R is known — so the module reports both, and the verification report says which half is evidence |
| D-37 | The PPG periodicity gate is set conservatively and its residual error is published | Tune the gate until the table looks clean, or report the mean and omit the outliers | Unlike the red/IR correlation gate, periodicity does not separate: accurate windows reach down to 0.199 and inaccurate ones up to 0.746, so no threshold keeps every good window and refuses every bad one. 0.50 cuts wrong readings from nine to two while keeping 87 % of windows; roughly 1 % can still be wrong by up to 25 bpm and the report says so. The real fix is not a sharper single-signal threshold but cross-checking PPG pulse rate against ECG heart rate — two independent measurements of one quantity disagreeing is stronger evidence than either can produce alone |
| D-47 | The silence during an acquisition interruption is not counted against the patient afterwards | Keep one continuous "time since last beat" | After ten seconds of leads-off plus three of settling, that counter reads thirteen seconds, so asystole fires the instant signal quality returns — before the patient has had any opportunity to produce a beat the system was willing to look at. It is the first asystole bug (BUILD_LOG 005) from the other direction: not alarming because nothing was ever measured, but because measuring was deliberately stopped. `RollingHeartRate.restart()` moves the clock forward with the detector restart (D-22) |
| D-51 | The signal-quality gate withholds a rate only when energy concentration AND the detector's own signal-to-noise estimate are both low | Concentration alone | The concentration statistic is rate-confounded: above ~125 bpm the QRS bumps crowd together and a clean tachycardia scores below the gate — silencing the monitor for exactly the rhythm it exists to alarm on. Found by a person following TESTING.md when the tachycardia alarm never fired; every automated test had used ≤104 bpm. Neither statistic separates alone (clean-180 and wrong-72 overlap on both), but the failure regions differ, so the AND keeps 130–150 bpm reportable while every noise case that produced a wrong rate stays withheld. A clean ~180 bpm remains withheld — a documented residual, not a silent one |

### Hardware and firmware

Verifying acquisition without a board, and the target-specific choices that remain.

| ID | Decision | Alternative rejected | Why |
|---|---|---|---|
| D-24 | Acquisition phases re-cut as simulation; physical bring-up demoted to a backlog | Wait for hardware and keep the plan as written | The board did not arrive and its date is unknown. A plan whose next unchecked box cannot be worked is not a plan. Everything above the ADC pins can be verified without it — and modelling the ADC, quantisation and electrode behaviour explicitly produces a *stronger* claim than clean-millivolt validation, because the pipeline is then scored on what the device would really see |
| D-26 | Front-end gain 330, sized from the ±5 mV input range IEC 60601-2-27 expects | The AD8232 datasheet's ~1100 heart-rate-monitor gain | The reference design assumes a ~1.5 mV signal. Run against real recordings the model clipped: records 203 and 208 exceed 4 mV, and clipping a QRS is losing the feature the whole device exists to find. 330 puts ±5 mV inside the rails and still resolves 2.44 µV per LSB — 41 codes across a 0.1 mV feature — so the resolution given up costs nothing measurable |
| D-27 | Device buffer overwrites the oldest samples when it overflows, and counts the loss | Refuse new samples once full / grow the buffer | Past the buffered window something must be lost, and for a monitor the recent samples are the ones worth keeping — a clinician needs to know what the patient is doing now, not what they were doing during the outage. Growing the buffer on an ESP32 risks a failed allocation at exactly the moment the link is already broken. The counter is what turns the loss from invisible into reportable |
| D-28 | Leads-off debounce is asymmetric — 50 ms to assert, 500 ms to clear | One symmetric debounce | Asserting is a safety condition and shares SR-03's 2 s budget with the server's 1.5 s alarm debounce, so it has to be short — sizing it without knowing the server's number is how D-18 happened. Clearing is slow because a flapping electrode must not produce an alternating status, and because the amplifier needs to settle after reconnection anyway (D-22) |
| D-29 | The sampling ISR only gives a semaphore; the ADC is read in a task pinned to core 1 | Read the ADC inside the ISR | An ISR doing an ADC conversion holds off everything else for the duration, and `analogRead` is not guaranteed IRAM-resident — a flash cache miss inside it would stall at unpredictable moments. Waking a high-priority pinned task moves the work off the interrupt path and leaves only scheduling jitter, which the AFE model measured as costing 3.6 LSB RMS at 200 µs — well inside budget. Core 1 because core 0 runs the WiFi driver's long interrupt-disabled sections |
| D-30 | The Espressif platform version is pinned in `platformio.ini` | Track the latest core | Arduino-ESP32 changed its hardware-timer API incompatibly between 2.x and 3.x. An unpinned build can change the behaviour of a 360 Hz acquisition path with nobody editing a line, and the first symptom would be a wrong heart rate rather than a compile error |
| D-31 | The firmware has two transports behind one frame builder — WebSocket and serial | Two firmware images, or no simulator support | Wokwi has no route to a local ingest server, so a WebSocket-only image cannot be simulated at all. Splitting only the transport keeps the frames byte-identical between the two, because both call the same `vs_frame_build()`; a second image would be a second thing to keep correct |

### Persistence and operations

What is stored, what is optional, and what a display must never do.

| ID | Decision | Alternative rejected | Why |
|---|---|---|---|
| D-21 | Dashboard is a self-contained canvas page served by the existing server | Separate Next.js app (as originally planned) | One process and no build step means the demo starts with a single command and cannot fail on an unfamiliar machine mid-interview. Next.js is already demonstrated by AsyncForge and SonicScribe, so nothing is lost by right-sizing here |
| D-42 | History stores 1 Hz derived numbers and alarm episodes; the waveform is not stored | Persist every frame, including raw ECG | At 360 Hz one patient generates ~250 MB of raw ECG per day, and a twenty-bed ward 5 GB/day before indexes. Real central stations do keep waveform — in compressed fixed windows with a retention policy and tiered storage — which is a project of its own and not what this one demonstrates. 1 Hz numerics keep trends, export and alarm review working at ~1/3000th of the volume. An alarm is stored as one row per *episode*, not per evaluation, or the count would depend on the tick rate rather than on the patient |
| D-43 | The server runs with no database, and a database failure degrades to "no history" | Require PostgreSQL, or fail on a write error | A bedside monitor that stops displaying a patient because a disk filled up has confused its priorities. Persistence writes are fire-and-forget off the ingest path, a failing pool disables itself with one loud message rather than throwing per query, and `DATABASE_URL` being unset is a supported configuration — the demo still starts with one command (D-21). The storage *contract* is verified without a database by running the same test suite against an in-memory implementation, so only the SQL binding needs the container (the D-25 pattern applied to infrastructure) |
| D-45 | Storage tests must not assume an empty store | Truncate the database between tests | A real database keeps rows from earlier runs, and that is the normal case in production — a contract that only holds on a clean store is not the contract the system runs under. The in-memory implementation hid this by starting fresh every time; the first run against PostgreSQL failed immediately. Tests now tag their own rows and assert only about those |
| D-48 | A bed stays on the central station after its device disappears, marked offline | Remove the tile when the stream stops | A tile vanishing is indistinguishable from a patient being fine — the screen looks calmer at exactly the moment it should not. Beds persist for ten minutes marked offline, and losing the link to the *server* clears nothing at all, because a dropped WebSocket is not evidence about any patient. Tiles also sort by worst active alarm rather than by bed number: a central station exists to say who needs attention first, and ordering by name buries that under an accident of naming |

### Verification method

How claims in this repository are made checkable.

| ID | Decision | Alternative rejected | Why |
|---|---|---|---|
| D-40 | Windows where the bedside reference itself moves are excluded from scoring, and the exclusion is reported | Score every window against the reference median | A monitor's pulse numeric is an estimate too, updated every second and smoothed by its own algorithm. Comparing a stable 30 s estimate against a reference that swings 50–70 bpm inside the same window measures the reference's variability, not this pipeline's error — and it was: the apparent 25 bpm outliers were windows where our ECG and PPG agreed with each other to 1.4 bpm while the reference disagreed with itself by 20. Excluding 28 of 160 windows takes mean error from 1.04 to 0.73 bpm and 98.6 % to 100 % within ±5; the count excluded is published so the filter cannot flatter the result silently |
| D-41 | The rate cross-check is asymmetric: a low pulse is a finding, a high pulse is an error | Flag any disagreement beyond a tolerance | The physiology is not symmetric. Fewer pulses than beats is *pulse deficit* — in atrial fibrillation and frequent ectopy some beats are too weak to open the aortic valve and never reach the finger — which is a sign a clinician wants to see, so both numbers stay on screen and the disagreement is named. More pulses than beats is impossible, since every pulse needs a beat behind it, so the pulse rate is withheld. A pulse near exactly half the heart rate is the signature of sub-harmonic lock (D-36) and is withheld too |
| D-46 | The replay simulator warns when `--speed` compresses a fault below the alarm that should catch it | Leave the speed and the scenarios independent | Scenario windows are simulated time; alarm debounces are wall-clock, because a debounce protecting a clinician has to be. At 15× a ten-second detached electrode lasts 0.67 s of real time and a 1.5 s debounce correctly refuses to fire — so the demo silently shows no alarm and looks like a broken alarm engine rather than a badly chosen clock. Found by doing exactly that |
| D-49 | Requirements are verified by fault injection against the running system, not only by unit tests | Trust the component tests that already pass | Every component of the signal-quality gate passed its own tests and the shipped monitor still reported 102 wrong heart rates on a swamped signal — because the metric existed only in Python and the server never called it. A requirement is a property of the *system*; testing its parts is not the same claim. The matrix starts the real server, speaks the real protocol, injects one fault and measures one number |
| D-50 | `docs/requirements.md` is generated from a requirement model plus measured evidence | Keep the requirements table as prose and update it by hand | Exactly the argument behind D-11, applied one level up: a hand-maintained status table drifts silently, and the drift is invisible because the table still looks authoritative. Status is now *computed* — a requirement whose evidence has never been produced renders as "not yet measured", and one whose evidence says it failed cannot be rendered as passing because nothing in the generator can express that. Traceability is computed too, so a user need with no requirement behind it shows up as an empty row |

## The one that recurs

Eight decisions — D-08, D-22, D-23, D-32, D-34, D-37, D-47, D-51 — are the same decision in
different places: **a monitor that declines to answer is safe; one that answers wrongly is
not.** They were not planned as a theme. Each was forced by a specific failure:

- a detached electrode producing a confident heart rate from numerical residue (D-08);
- reconnection fabricating 190 bpm tachycardia with signal quality "good" (D-22);
- a stale number staying on screen after the device went silent (D-23);
- motion artefact reported as an 8-point desaturation, self-consistently (D-32);
- a calibration curve that cannot be validated in simulation being presented as if it had
  been (D-34);
- a periodicity gate that does not fully separate good readings from bad (D-37);
- the silence during an interruption charged to the patient afterwards (D-47).

Five of the eight were found by *running* the system rather than by testing it, and three
were found by a second implementation disagreeing with the first.
